# 精致感从哪来：hsmkrt1996.com 拆解与对照

调研日期：2026-09-17　对象：`https://hsmkrt1996.com/`（Hisami Kurita 作品集，Nuxt 2 SSR）

方法同前：CDP 在页面脚本执行前注入探针，劫持 `getContext` / `shaderSource` / `addEventListener`，并对打包产物做关键词频次统计。所有关于该站的断言均来自实测，示例代码为原创。

---

## 摘要：结论和你可能预期的不一样

我原本以为"精致感"会来自复杂的渲染。**实测结果是反的。**

这个站点的全部视觉资产是：**18 张 webp + 1 个字体 + 40 个请求**。没有 3D 模型、没有 HDR 环境贴图、没有后期管线。整个 WebGL 部分只有 **2 个着色器**（182 和 1911 字符），做**一个**效果。

它的精致感来自四件事，按贡献从大到小：

| # | 来源 | 实测证据 |
|---|---|---|
| 1 | **动效词汇极度克制** | 全站只有 **2 条**贝塞尔曲线；`.2s` 被用了 **28 次** |
| 2 | **多状态自定义光标系统** | 至少 4 套独立 DOM：idle / action / loading / click-hold |
| 3 | 一个 WebGL metaball 揭示效果 | 单个片元着色器，1911 字符 |
| 4 | 滚动劫持 + 编排 | `wheel` 被 `preventDefault`，166 个 scroll 监听器 |

**第 1 条是最便宜也最有效的，而它恰好是你现在最薄弱的一环。**

## 2. 精致感来源 #1：动效词汇的极度克制

这是整份报告最重要的数据。

### 它的全部缓动曲线

```
cubic-bezier(.26,.16,.1,1)   ×5
cubic-bezier(.43,.05,.17,1)  ×2
```

加上 GSAP 命名缓动：`power1.in` ×6、`power3.out` ×1、`power1.inOut` ×1、`expo.out` ×1。

**整个站点，两条自定义曲线。**

### 它的时长分布

```
.2s   ████████████████████████████  28 次   ← 绝对主力
.3s   ████████                       8 次
.08s  ██████                         6 次   ← 微反馈（按压级）
.28s  ███                            3 次
.18s  ██                             2 次
──────────────────────────────────────────
.78 / .92 / 1 / 1.18 / 1.2 / 2.98s        ← 只用于编排好的入场/区块序列
```

**三个时长（.2 / .3 / .08）覆盖了 42 次使用**，剩下的长时长全部留给有意编排的序列。

这构成一套清晰的分层：

| 层级 | 时长 | 用途 |
|---|---|---|
| 微反馈 | **.08s** | 按下、即时状态切换 |
| 标准 | **.2s** | 绝大多数悬停、显隐、位移 |
| 次级 | **.3s** | 稍大的元素、需要被看见的变化 |
| 编排 | 0.8–3s | 入场序列、区块转场，**只在这一层花时间** |

## 3. 你现在的词汇（实测你的仓库）

同样的方法跑你的代码：

**缓动**（framer-motion）：
```
"easeOut"          ×11
[.22,.72,.2,1]     ×5
"none"             ×3
'easeIn'           ×1
[.2,.7,.3,1]       ×1
"easeInOut"        ×1
```

**时长**（`.tsx` 里的 `duration:`）：
```
.1 ×5 · .35 ×1 · .24 ×1 · .18 ×2 · .16 ×1 · .15 ×2 · .14 ×1 · .12 ×1 · .09 ×1
```

**CSS 过渡**：`.18s` ×2、`.13s` ×2；缓动只有 `ease-out` ×1 和 `cubic-bezier(.2,.7,.3,1)` ×1。

> 核对说明：初次统计时出现过 `linear` ×14，复核发现**全部来自 `linear-gradient`**，与缓动无关，已剔除。

### 诊断

| | hsmkrt | 你 |
|---|---|---|
| 自定义曲线数量 | **2** | **2 条，但几乎一样** |
| 最常用时长的使用次数 | .2s ×28 | .1s ×5 |
| 不同时长的数量 | 3 个主力 + 编排层 | **9 个，其中 6 个只用过一次** |

**两个具体问题：**

**问题一：两条几乎一样的曲线并存。**

```
[.22, .72, .2, .1→1]   ← 在 Portfolio 等处
[.2,  .7,  .3, 1]      ← 在 Deck.module.css 等处
```

这两条肉眼分辨不出差别，但它们的存在意味着**没有单一事实源**。以后每加一个组件，就多一次"抄哪条"的随机选择，曲线会继续漂移。

**问题二：时长各写各的。**

`.09 / .1 / .12 / .14 / .15 / .16 / .18 / .24 / .35` —— 九个值，六个只用过一次。这些数字之间的差异（比如 .14 和 .15）**人眼完全无法分辨**，但它们让整个站点缺少一种"同一只手做出来"的统一节奏。

**这正是"缺少精致质感"最主要的来源** —— 不是某个动画不够花哨，而是几十个动画各自为政。

## 4. 精致感来源 #2：多状态光标系统

实测到的光标相关 DOM（全部带独立 transform）：

```
.mouse                    ← 位置载体，transform 跟随指针
.mouse-action             ← "可交互"状态
.mouse-action-wrapper     ← 带 ~8° 旋转：matrix(0.990268, 0.139173, …)
.mouse-action-block
.mouse-loading            ← "加载中"状态
.mouse-loading-wrapper    ← 同样 ~8° 旋转
.mouse-loading-block
.mouse-img-click          ← 点击瞬间（scale 0 → 1）
.mouse-img-hold           ← 按住态（scale 1.3）
```

**至少 4 个独立状态**，每个都有自己的 DOM 和变换。那个 8° 的固定旋转是个很有意思的细节 —— 让光标元素**不完全水平**，脱离"系统 UI"的感觉。

这是纯 DOM + transform 实现的，**零渲染成本**，但对"这个站被认真做过"的感知贡献极大。

### 值得注意的是它没有做什么

它**没有**把系统光标藏掉换成一个跟随的圆点（那是最常见也最廉价的做法）。截图里能看到光标仍是一个明确的**指向手形图标** —— 它增强了指针的语义，而不是取代它。

## 5. 精致感来源 #3：一个 WebGL 揭示效果

单个片元着色器（1911 字符），uniform 完全暴露了它的意图：

```
u_metaballsPos      vec2     ← 融球位置
u_metaballsRadius   float    ← 半径
u_mouse             vec2     ← 指针
u_time              float
u_rand              float    ← 随机种子
u_texture           sampler2D ← 被揭示的图
u_texturesize       vec2
u_resolution        vec2
```

**一个跟随指针的融球，透过它采样照片。** 截图里可以看到：纯蓝色平面上，若干圆形区域里透出下面的人物照片，圆与圆靠近时边缘会像液体一样融合 —— 这就是 metaball 的特征。

原创的最小实现思路（不是它的代码）：

```glsl
// metaball 的核心：多个球的"影响场"相加，再阈值化
// 单个球的场强 = r² / d²，距离越近场强越大
float field(vec2 p, vec2 center, float r) {
  vec2 d = p - center;
  return (r * r) / (dot(d, d) + 1e-4);
}

void main() {
  vec2 p = gl_FragCoord.xy / u_resolution;
  float f = 0.0;
  for (int i = 0; i < BALL_COUNT; i++) f += field(p, ballPos[i], ballRadius[i]);

  // 阈值附近用 smoothstep 得到柔和边缘；场强相加是"融合"的来源
  float mask = smoothstep(0.95, 1.05, f);
  vec3 photo = texture(u_texture, p).rgb;
  fragColor = vec4(mix(u_bgColor, photo, mask), 1.0);
}
```

**关键在于"场强相加"**：两个球靠近时各自的场在中间叠加超过阈值，于是边界自然连成一片 —— 这个融合效果是加法的副产物，不需要额外几何计算。

## 6. 精致感来源 #4：滚动劫持

实测：

- 文档真实高度 **8114px**（用撑高元素占位）
- `wheel` 事件**被 `preventDefault`**（已验证 `defaultPrevented === true`）
- **166 个 scroll 监听器 + 45 个 wheel 监听器**
- `<html>` 的 `transform` 为 `none` —— 说明不是 transform 虚拟滚动，而是**程序化设置 `scrollTop`**

也就是：接管滚轮 → 自己维护一个目标位置 → 每帧向目标插值 → 写回 `scrollTop`。这是 Lenis / Locomotive 那一类平滑滚动的标准做法（未检测到这两个库的全局变量，可能是自己实现或已打包）。

**⚠️ 这一节有我没能测到的部分，必须说明：**

我用 CDP 的 `dispatchMouseEvent{type:'mouseWheel'}` 和 `Input.synthesizeScrollGesture` 都**无法驱动它滚动**（`scrollY` 始终为 0）。页面存在一个 `z-index:100` 的 `.loading` 门控元素，合成事件似乎被它拦截或未被识别为可信输入。

因此：

- **未能测得**平滑滚动的插值系数、缓动手感
- **未能观察到**滚动过程中区块之间的实际转场动画
- 后面四张深度截图是用 `scrollTop = N` 强制跳转拍的，**绕开了它的平滑滚动**，只能反映静态排版，不能反映转场

这部分若要补齐，需要人工在真实浏览器里操作并录屏。

## 7. 可落地的打磨清单（按性价比排序）

### ★★★★★ 第一优先：建立单一的动效词汇表

这是投入产出比最高的一件事，而且**不需要写任何新效果**。

建议建一个 `components/portfolio/motion.ts`（原创示例）：

```ts
/** 全站唯一的动效词汇表。新增动画一律从这里取值，不要就地写数字。 */
export const EASE = {
  /** 标准曲线：快出慢收，用于绝大多数进入与位移 */
  out: [0.2, 0.7, 0.3, 1] as const,
  /** 双向曲线：仅用于需要来回的状态（开合、切换） */
  inOut: [0.43, 0.05, 0.17, 1] as const,
} as const;

export const DUR = {
  /** 微反馈：按下、即时状态切换 */
  tap: 0.08,
  /** 标准：悬停、显隐、位移 —— 应该占你全部动画的大多数 */
  base: 0.2,
  /** 次级：较大元素、需要被注意到的变化 */
  slow: 0.3,
} as const;

/** 编排层：只有入场序列、区块转场才配用这一档 */
export const STAGE = { enter: 0.8, sequence: 1.2 } as const;
```

然后把现有的 `.09 / .1 / .12 / .14 / .15 / .16 / .18 / .24 / .35` **全部归并到 `tap / base / slow` 三档**，把 `[.22,.72,.2,1]` 和 `[.2,.7,.3,1]` 合并成一条。

你会发现绝大多数改动是"把 .15 改成 .2"这种看似无意义的调整 —— **但整体感受的变化是显著的**，因为整个站第一次有了统一节奏。

> 这一条和上一份报告的结论一致，但这次有了对照数据：人家 `.2s` 用 28 次，你最常用的值只用了 5 次。

### ★★★★ 第二优先：非对称时序

你的 CD 机按键已经做对了（按下 rate 55、回弹 rate 20），但**只有那一处**。

原则：**进入快、退出慢**（或反过来，取决于语义），但绝不能一样。

| 场景 | 进入 | 退出 |
|---|---|---|
| 按键按下 / 抬起 | `tap` (.08) | `base` (.2) |
| 悬停进入 / 离开 | `tap` (.08) | `base` (.2) |
| 面板打开 / 关闭 | `slow` (.3) | `base` (.2) |

### ★★★★ 第三优先：光标状态

你已经有一个很强的基础 —— 整站是拟物的（CD 机、CRT）。加一层**语义化光标**会非常契合：

- 可点击的 3D 元件上 → 光标变成一个小的指示形态
- 拖动音量旋钮时 → 变成"拖动中"态
- 加载/换碟时 → 变成等待态

**注意学它没做的事**：不要藏掉系统光标换成一个跟随圆点。在你这种"能真的操作"的界面上，指针的准确位置是功能性的。

成本：纯 DOM + transform，不碰渲染管线。

### ★★★ 第四优先：滚动节奏

你目前是原生滚动（`Portfolio.tsx` 里只设了 `scrollBehavior: smooth/auto`）。

你已经装了 `@studio-freight/lenis ^1.0.42` **但没有使用**（全仓库无引用）。如果要做平滑滚动，它就是对方那套机制的成熟实现。

但要提醒：平滑滚动是**有争议**的取舍 —— 它会让滚动与输入设备解耦，部分用户（尤其触控板用户）会觉得"粘滞"。而且必须接上你已有的 `prefers-reduced-motion` 通路。**建议放在词汇表统一之后再考虑**，不要作为优先项。

### ★★ 不建议的方向

- **不要**加 metaball 揭示效果。它和你的拟物/印刷美学是冲突的 —— 对方那是平面设计语言，你是器材质感语言。
- **不要**为了"更多动效"而加动效。对方的克制是特点，不是限制。

## 8. 一句话总结

> 对方的精致感不来自技术密度，来自**决策密度**。
> 18 张图、2 条曲线、3 个时长、1 个着色器 —— 每一项都是被决定过的，而不是随手写的。
>
> 你的站点在**技术上已经超过它**（真实 3D 机构、音频分析、解谜终端），
> 差的是那层把所有零件统一起来的节奏。而那层几乎不要钱。
